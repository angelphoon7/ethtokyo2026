# 07B — Independent Problem Validation After Concept Freeze

**Research checked:** 25 September 2026. **Inputs:** `07_PROJECT_FREEZE(5).md` and `00_HACKATHON_CONTEXT(20260925-204751).md`. **Method:** desk research of official protocol/event/API documents, product documentation, developer accounts, research papers, and ETHGlobal submissions. No interviews, live API calls, real x402 purchase, or signer instrumentation were performed for this report.

## 1. Executive verdict and scope

**HOLD — TARGETED EVIDENCE OR SPIKE REQUIRED.**

The freeze proposes a *buyer-side, owner-scoped, pre-sign* gate for one unattended x402 API purchase. This matches an officially described Intercepta prize integration, and the payment standard exposes the relevant quote fields. Neither fact establishes that a real operator frequently encounters a quote that passes endpoint/token/budget rules yet deserves a different decision because of an external `payTo` risk signal. I found no independently documented buyer incident or operator adoption decision for that **exact** residual failure. Several existing products claim essentially the same buyer decision. On current evidence, the defensible pitch is **a sponsor integration demonstration with an unvalidated customer need**, not a validated market problem or a proven finalist differentiator. [ETHGlobal prize](https://ethglobal.com/events/tokyo2026/prizes); [x402 v2 specification](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md); [402Sentinel](https://402sentinel.com/); [t54](https://docs.t54.ai/docs/products/x402-secure).

**Scope integrity.** The attached freeze agrees with the prompt's scoped-agent-purchase hypothesis. Its previous merchant-to-payout authority/ENS branch was explicitly stopped and superseded. Evidence about a seller's authority to name a recipient, ENS control, or merchant identity cannot be transferred to this question. Here an external address-risk signal may change a **buyer's** pre-sign decision; it cannot certify seller identity or delivery.

## 2. Canonical user and problem

**Unverified target user:** a developer/operator who owns the payer signer for an unattended agent tasked with buying one defined API result. The operator chooses approved HTTPS endpoint(s), an x402 scheme/network/token, per-call and task budgets, and a signing service the agent cannot access directly. The agent receives an HTTP 402, selects a requirement, and either obtains a paid result or pauses. [The official buyer quickstart](https://docs.x402.org/getting-started/quickstart-for-buyers) demonstrates automatic payment from a registered EVM signer; [Coinbase's agentic wallet](https://docs.cdp.coinbase.com/agentic-wallet/mcp/mcp-tools/overview) already supports automated x402 requests and owner-set per-call/session spending limits.

**Precise hypothesized residual:** an allowed endpoint offers a quote whose scheme, chain, asset, amount, and task budget all pass, but its actual `payTo` has a timely external risk signal the operator would regard as sufficient to stop or review before the only signer creates an authorization. The potential consequence is a payment the owner would have refused. Neither the prevalence of such quotes nor the cost relative to using a trusted provider or manual approval has been shown.

**Existing controls:** endpoint/TLS selection, pinned token and chain, spending and velocity caps, static recipient allowlist, scoped signer/wallet policies, manual approvals, and post-payment monitoring. A static `payTo` allowlist plus a trusted endpoint may leave almost no room for a live recipient signal. If the operator deliberately permits dynamic payees, the live signal may matter; its error rate, coverage, cost, and latency then matter too. A risk indicator also cannot establish control of an endpoint or good API output.

**Why now, with limits:** official x402 clients can perform a 402-to-signed-payment retry automatically, and ETHGlobal has created an agent-payment screening prize. That makes a test timely. It does not prove a growing rate of risky allowed quotes or an operator willingness to pay for another check. [Buyer quickstart](https://docs.x402.org/getting-started/quickstart-for-buyers); [prize](https://ethglobal.com/events/tokyo2026/prizes).

## 5. Adversarial findings

1. **Static trust may dominate.** For one known HTTPS endpoint and one known seller, pinning its expected `payTo`, token, network and price can reject an unexpected recipient deterministically. If payees legitimately rotate, the operator might instead approve a new address manually. A risk feed adds little when every recipient is already pinned; monitoring alone cannot undo a settled payment, but is an adequate choice if the dollar risk is tiny.
2. **The signal may not answer the actual question.** A risky address flag is neither proof of endpoint compromise nor evidence that the API will fail. A clean address can be fresh, misattributed or controlled by a bad seller. Mainnet intelligence about the same address on testnet cannot prove a testnet seller is malicious. Controlled known-risk fixtures prove only integration. [Prize](https://ethglobal.com/events/tokyo2026/prizes); [Quick Scan](https://docs.web3antivirus.io/reference/quick-scan-address).
3. **False holds can defeat the job.** Legitimate treasury rotation, payout aggregators and shared wallets can confuse simple risk heuristics; the [Frisk correction](https://tryfrisk.dev/blog/a-payto-swap-is-not-a-honeypot/) provides a concrete caution, not a measured Intercepta error rate. Fail-closed unknown/outage policy stops even legitimate tasks. For low-value API calls, human-review cost and delayed results may exceed the worst bounded loss.
4. **Signer bypass is decisive.** An automatic x402 wrapper with direct access to a funded signer may sign before an app-level after-the-fact check. Guarding one tool is insufficient if the agent can reach another wallet/tool, raw key, browser wallet, or alternate payment route. [Official buyer quickstart](https://docs.x402.org/getting-started/quickstart-for-buyers). The claim requires code-level inspection and a zero-sign-call test on the selected version.
5. **Quote/authorization mismatch and delivery risk persist.** Screen the same selected `accepts[]` requirement, then check typed-data transfer `to`, amount, token domain and validity at the signer. Unsupported role-constant payees and other schemes must hold. A basic authorization does not guarantee the paid API body. [x402 v2 spec](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md); [five attack study](https://arxiv.org/abs/2605.11781).
6. **Unit economics and privacy are unmeasured.** Per-call external checks add network delay, API dependencies and disclosure of payee/purchase timing; a busy worker may face review queues. Neither live scan latency, commercial price, hit rate, false-positive rate nor owner tolerance has been measured. Do not assume micro-payments justify micro-screening or vice versa.
7. **Hackathon risk is real.** The [event rules](https://ethglobal.com/events/tokyo2026/info/details) state a Sep 27 09:00 JST submission deadline, require Start Fresh project work to begin after official start, and require disclosure of AI-assisted work. Work dates and selected track are team facts, not supplied here. The [sponsor rules](https://ethglobal.com/events/tokyo2026/prizes) require a live call and both branches; obtaining a key, compatible verdict and real paid service in time are open dependencies.

## 6. Incremental-value test — same quote

**Status: proposed controlled experiment, not an observed risk verdict or live purchase.** No team-selected paid service or captured 402 was supplied. To make the comparison unambiguous, use the *published x402 v2 example* as a **format fixture only**, then replace every illustrative field with one saved, live quote before claiming a result. The spec's sample is `GET https://api.example.com/premium-data`, `exact`, `eip155:84532`, asset `0x036CbD53842c5426634e7929541eC2318f3dCF7e`, amount `10000` base units (0.01 for a six-decimal token), `payTo` `0x209693Bc6afc0C5328bA36FaF03C514EF312287C`. Example values are **not** evidence that this service or address can be purchased or has risk. [Official example](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md).

Once a real 402 is captured, fix one owner task and local policy (approved endpoint, exact scheme/network/token, per-call cap ≥ quote amount, available task budget; recipient not statically rejected). Compare the **identical raw selected quote**, without changing the recipient between arms:

| Arm | Decision on the identical captured quote | Evidence needed to make the result real |
| --- | --- | --- |
| **A. Local buyer controls only** | If all owner rules pass, authorize one bounded attempt. If static payee pinning is part of the operator's actual baseline and this payee is absent, it **holds already**; there is then no demonstrated added decision. | Saved raw 402, recorded local checks, signing-call count, baseline risk and cap. Do not pay merely to manufacture an A/B outcome; a dry run can compare decisions. |
| **B. Same local rules plus live Intercepta** | Approve only under an explicitly justified mapping of actual documented response fields. If a live, interpretable signal maps to hold while A passes, permit **zero** signer calls and show the reason. Unknown/error also holds, but outage alone is not evidence of recipient risk. | Timestamped live response to the **same actual selected EVM `payTo`**, sanitized response and mapping, duration, and signer counter; testnet address screened as a mainnet-address subject under sponsor rules. |
| **C. Manual hold** | Ask the owner before signing. They may reject or approve after reviewing the same quote and signal; if the owner always chooses review, B's incremental benefit must be shorter time, fewer reviews, or better decisions. | Operator's actual process/time and what information changes their decision; no invented approval preference. |

**Interpretation:** A=B on an allowed quote means no incremental decision; A=B on a held quote means local controls suffice. A allows while B holds on a **live justified finding** proves the technical intervention works for a controlled case, *not* a frequent real-world problem. Even that result should be tested against C and a verified real operator decision before a product-need claim. A sponsor-provided risky fixture is useful for B, but must be labeled a controlled test.

## 8. Next action and kill criteria

**Proof 1 — operator need, bounded to one day of focused outreach/review:** ask at least **two independent operators or maintainers actually running, deploying, or seriously implementing unattended paid x402 calls** to walk through a recent real purchase/quote, payer controls, whether `payTo` can change under an allowed endpoint, present approval practice, held-task cost and whether an external risk result would change a concrete decision. Request a redacted trace or reproducible documented example where possible. Separate builder/vendor enthusiasm from paying-operator demand. **Reopen problem gate** only if at least one credible real workflow has a specific allowed quote whose counterparty risk matters materially *despite current controls*, and a second independent signal supports recurrence or high consequence. If none can identify such a workflow and static pinning/manual review suffices, **STOP/REOPEN Steps 6–7 for a different user problem**. Two conversations are an economical gate, not statistical market validation.

**Proof 2 — same-quote live incremental decision, bounded to a short technical spike:** capture one real supported 402; compare A and B without altering selected terms; acquire a live Intercepta response for that `payTo` and a documented sponsor risk fixture if necessary; show a justified allowed branch and locally permitted held branch, with zero signing calls on the hold. Measure latency and distinguish unknown/outage. **Reopen technical feasibility** if the response semantics can be mapped honestly and the seller's actual payee is screened before signing. **Stop the Intercepta partner-prize path** if a real live API response cannot affect a pre-sign action, the only held case is hard-coded, or all available payees fail local policy anyway. Controlled fixture success remains labeled controlled, never an incident.

**Separate Codex/Step 9 signer experiment (not product build):** inspect the exact selected official x402 client package and `ExactEvmScheme` signing path; give the agent access only to a guarded payment tool and a non-exportable/restricted signer interface. Inputs: one real 402, an approved mapped response, a held mapped response, a quote mutated after screening (`payTo`/amount/asset/chain), and an attempt to invoke the unguarded wrapper. Outputs: raw challenge and selected requirement, count/timing of signer invocations, decoded signed authorization fields, payment/settlement evidence for the allowed case, and a blocked bypass/mutation trace. **Pass** only if allowed terms match exactly, an allowed payment really settles, every held/mutated/bypass case has zero payer authorization signatures, and no agent-visible tool/key can invoke another funded signer. **Fail** if a convenience wrapper signs first, alternate route reaches the key, or payment evidence consists only of a simulated 402. Allocate an initial two-hour spike and cut optional UI/provider work if the boundary is unresolved.

**Decision for the human:** retaining this freeze as a limited sponsor prototype is reasonable if both live technical checks pass. Claiming a broadly needed product or strong finalist differentiation is premature. If the operator proof fails, the problem gate remains closed even if the prize demo works.
